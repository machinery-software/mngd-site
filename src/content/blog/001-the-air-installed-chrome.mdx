The console row under the verdict is my favorite thing I've shipped, because it refuses to flatter me: *"a package on a Mac proves the Mac has it, never on its own that this declaration is why — the row above is where that is settled."* The row above is the device, in its own words, naming the file.

That's the claim this project makes, so let me state it precisely: the software is on that Mac because a file in a repository said so, and the Mac is the one saying it.

## What I'm building, in one paragraph

**mngd** is an Apple MDM that treats git as the source of truth and Apple's declarative management (DDM) as the delivery mechanism. Your fleet's desired state is a directory of declaration files; changing the fleet is a reviewed change with a diff. The part that surprises people: the repository lives *inside* the product. mngd hosts the fleet repo itself — propose, review, gates, and merge all happen in the console, with no forge, no external CI service, and no token. The gates run in-process and refuse in plain English, citing their own decision history. And the console shows desired state next to what each device actually reported — when it says an app is installed, that's the device attesting it, not the server assuming it. Config-as-code device management isn't new; Fleet and Zentral do good work putting fleet config in git beside the MDM. I haven't seen another MDM that hosts the repository itself. If you have, tell me and I'll link it here.

## I asked for Chrome on September 4. I got it on September 11.

Every day in between, the thing refusing me was my own product — and every refusal was correct.

The deploy refused to move. I'd merged a fix and run the deploy, and it stopped cold: *"origin/main is AHEAD of the newest published image… Deploying now would put an image older than what you just pushed to main onto this host… Nothing has been changed here: .env is untouched and no container was recreated."* CI hadn't finished publishing. A deploy that proceeded would have silently shipped stale code while looking like it worked. It refused before touching anything, and told me exactly what to wait for.

The gates refused my own history. When I proposed the Chrome change, lint rejected the repository's *own shape*: an installer was still sitting in git as raw bytes, a layout an earlier decision had outlawed because every clone, every image build, every export and every seed of the repository would copy every app's installer, in every version anybody ever shipped, forever. The fix wasn't a hotfix or a migration script run in the dark. The repository migrated its own shape through a reviewed change: I read the diff, watched the gates go green on it, and applied it like any other change. The product's history is customer data; it doesn't get rewritten at boot, even by the product.

One refusal lied, and got caught by its own log. Early in the week a compile refused with "nothing was compiled" — after it had already written to the store devices are served from. Only luck (a no-op change) made the message true. The check now runs before anything is written, and the lesson went in the repo's ledger: a refusal is a receipt about the past — "nothing happened" must be true before it is said.

And one small honest detail: the change I opened on September 4 named Chrome 152.0.7977.83. The one that installed names 153.0.8010.37 — Google shipped a new Chrome while my own gates were holding the door. When the path finally cleared, the pipeline fetched the current installer from Google's own download server, streamed it through a hash, read its distribution manifest and signing chain, recorded the digest (`5b6419…12cb6`, 263,986,305 bytes) in a record the declaration cites, and generated the files the gates then judged.

A week from asked to installed, for one browser, is slow. But every one of those days was the product refusing to lie — about what was compiled, what was deployed, or what its own history required. The next app takes minutes, and it inherits every one of those refusals.

## Findings for Mac admins, from the failures on the way

These came out of the failed attempts that preceded the success, on real hardware:

**Flat component packages die silently.** Serve a plain component pkg — the kind `pkgbuild` makes, the kind plenty of vendors ship — through the declarative package channel, and the device downloads it, then fails without any error naming the format. The status walk we recorded was `1 queued → 3 downloading → 4 installing → 8 failed`, with `reasons = [installFailed]` and nothing anywhere naming the package format as the cause. The distribution-package form is what the OS accepts through this channel — Chrome ships one, which is part of why it's the app in this story. If your declarative install dies after the download completes, check your package format before you check anything else.

**The manifest wants chunked digests in practice.** Apple's schema reads as though a single hash suffices. Installs proceeded reliably only with the chunked `sha256-size`/`sha256s` form. I can't tell you why from the docs; I can tell you what worked.

## Why some of this took days to find

Absence of evidence kept masquerading as evidence. I once recorded "the installer process logged zero lines — it was never invoked" as a finding, and it turned out that process logs zero lines through this path even when the install succeeds. The instrument's silence carried no information, because I'd never shown the instrument could speak. That's now a rule in the repo, one of a growing list: a guard isn't a guard until you've seen it fail; an instrument's answer means nothing until the instrument has been shown to run; a fix isn't verified by the error going away but by the success arriving for the right reason.

That's the actual product thesis. Not the git part, not the single binary — the discipline. Every capability claim in this project has an evidence entry behind it: what was predicted, what the device reported, what would have falsified it. The claim in this post's opening scene is evidence entry E-130 in the repository. The console inherits the same discipline — a field the device never reported says *never reported*, in italics, instead of showing you a comforting default.

The week's best lesson came at my own expense. When the Chrome change went green and Applied, I called it installed. The device page is what corrected me: Applied means the desired state was written; installed is the device's word, and only the device gets to say it. I built that distinction into the product and still needed my own console to hold me to it.
